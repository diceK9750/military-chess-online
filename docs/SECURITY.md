# セキュリティ仕様

[GAME_RULES.md](GAME_RULES.md)の不完全情報性を保つ必須要件を定義する。[ARCHITECTURE.md](ARCHITECTURE.md)の候補技術を変更しても、本書の保護要件は維持する。現時点は文書のみであり、対策を実装・検証済みという意味ではない。

## 信頼境界と保護対象

プレイヤー自身がブラウザの開発者ツール、改変JavaScript、任意のHTTPクライアント、公開接続情報を使うことを想定する。クライアントの盤面・種類・手番・勝敗・時刻は信用しない。認証済み利用者でも、他人の情報の取得や直接更新は許可しない。

保護対象は敵の種類・秘密配置・軍旗の継承元、対局状態と履歴の完全性、アカウントと参加権限、秘密鍵、長期間の再開に必要な永続データ。サーバーとDBを判定の信頼境界とし、管理者・運用ログのアクセスも限定する。合法的な移動・結果からプレイヤーが推測することは防止対象外。

## 脅威と必須対策

| 脅威 | 経路・影響 | 必須対策 |
| --- | --- | --- |
| 敵駒情報漏洩 | API、初期HTML、JS、画像名、DOM属性、アクセシビリティラベル、LocalStorage、キャッシュ等から種類が判明 | サーバーで閲覧者別に出力を許可リスト化。敵の真の種類や軍旗継承元を一切送信しない。CSS等で隠すだけでは不可 |
| 履歴・配信経由の漏洩 | 棋譜、除去駒一覧、Realtime、通知、エクスポート、終了後表示 | 生の正本や内部戦闘記録を渡さない。状態と同じ秘匿を全経路へ適用し、対局終了後も敵種類を公開しない |
| 不正着手・改ざん | 相手駒操作、経路無視、手番偽装、戦闘結果やversionの上書き | 認証主体・参加権限・手番・状態・所有者・移動・戦闘をサーバー正本で再検証。クライアントによる状態の直接更新を禁止 |
| 二重着手・リプレイ | 二重タップ、複数端末、並列要求、タイムアウト後の再送 | version検証と対局単位の排他制御、request_idの一意制約、要求内容の照合。1手を状態・履歴・再送記録まで同一トランザクションで処理 |
| DB直接アクセス | 公開APIを迂回しREST・RPC等で秘密を読む／書く | 公開スキーマの対象テーブルにRLSと最小権限。秘密の正本はブラウザ用ロールに読み書きを許可しない。ビュー・関数・ストレージ・配信も監査 |
| 他対局へのアクセス | 対局ID列挙、他人の利用者ID申告、招待URL流出 | すべての要求で認証主体と参加関係を検証。参加者IDの申告を信用しない。招待は参加枠取得の権限に限定 |
| service role key等の流出 | フロントの環境変数、ビルド成果物、Git履歴、ログ | サーバーの秘密管理にのみ置き、フロント・Gitに保存しない。漏洩時は失効・ローテーションとアクセス調査を行う |
| 可用性・再開不能 | 不正要求の大量送信、データ消失、認証切れ | 入力サイズ・呼び出し頻度の制限、永続保存、バックアップと復旧検証を設計。セッション切れや長期不在で対局を終わらせない |

## 閲覧者別レスポンスの契約

認証済み参加者には自軍の種類・自分の除去駒の種類を返せる。敵については盤面上の位置・所属・生存／除去と合法的な着手・戦闘結果のみを返す。敵の種類のほか、それを直接表す内部ID、enum、並び順、画像参照、軍旗の実効種類なども返さない。識別子が必要な場合は種類から独立した不透明な値を使用する。

秘密配置の途中情報を相手に送らない。配置完了など進行に必要な状態だけを返す。エラー文・デバッグ応答・ログ・レスポンス差分が、非公開の判定理由を明かさないようにする。合法手のヒントAPIを設ける場合も、秘密種類を探索できる判定情報を追加しない。

秘密情報をHTML・JavaScript・LocalStorage等へ埋め込まない。許可された自軍情報は表示できるが、敵情報を含む全盤面をローカルへ保存してから隠す方式は禁止する。利用者別の応答を共有キャッシュへ保存しない。ログアウト・アカウント切替時には前利用者の盤面や認証情報を残さない。

## Supabase採用時の要件

- RLSを前提に設計する。ただしRLSだけで列の秘匿まで満たせると考えず、APIレスポンスから不要な情報を除外する。
- 匿名・認証済みブラウザ用ロールから秘密の正本を読めないようにする。閲覧者別APIの利用にも参加者チェックを課す。
- 更新は限定されたサーバー処理に集約する。関数の実行権限を限定し、権限昇格する関数を採用する場合は認証・参加権限確認、固定search_path等を設計する。
- service roleなどRLSを迂回できる権限を使用するサーバー処理でも、呼び出し利用者の権限を独立して検証する。
- ブラウザ向け公開接続キーは認可の代わりにならない。service role key等の秘密鍵とは区別し、公開キーでの直接アクセスも脅威モデルに含める。
- Authの検証済み主体を使用する。トークンやMagic Link、招待トークンをログ・解析サービスへ送らない。招待URLからの参照元漏洩も抑制する。

## 実装時に必要な検証（今回は未実施）

1. プレイヤーA・B・第三者・未認証の各立場で、状態・履歴・直接DB・RPC・配信へのアクセスを検査する。Aの敵種類がネットワーク応答やDOM等に含まれないことを確認する。
2. 不正手番、駒所有者偽装、経路違反、古いversion、同一request_idの内容変更、第三者要求を拒否し、盤面と履歴が変わらないことを確認する。
3. 並列要求・二重送信・コミット後の応答消失・処理途中失敗で、受理着手は1回だけ、盤面と履歴は一致し、中間状態が残らないことを検証する。
4. ブラウザ終了・別端末・再認証後に同じ対局を復元できること、非公開情報を含まず正しい手番・履歴が返ることを確認する。
5. ビルド成果物とGit履歴に秘密鍵がないこと、バックアップから復旧できることを確認する。

これは今後の受入条件である。認証・API・DBが未実装のため、現時点では安全性を実証していない。
