# セキュリティ仕様

[GAME_RULES.md](GAME_RULES.md)の不完全情報性と終局後公開を守る必須要件を定義する。[ARCHITECTURE.md](ARCHITECTURE.md)の候補技術を変更しても保護要件は維持する。文書化段階であり、対策を実装・検証済みという意味ではない。

## 信頼境界と情報区分

クライアントは信用しない。認証済みプレイヤーが開発者ツール、改変JavaScript、任意のHTTPクライアント、公開接続情報でアクセスすることを想定する。盤面・種類・手番・勝敗・終局状態・ルール版の自己申告を採用しない。

SECRET情報は敵の種類、秘密配置、軍旗の継承元・有効駒種、戦闘双方の種類を含む完全棋譜等を指す。対局開始前・PLAYING中は相手へ渡さない。自軍情報と合法的な移動・戦闘結果は表示可能で、そこからの推測は防止対象外。

終局後に限り、サーバーがコミット済み終局状態と認証済み参加者であることを確認したうえで、当該対局の全駒種類、LOCK時初期配置、完全棋譜、各戦闘双方の種類を双方へ閲覧可能にする。第三者・未認証者には終局後も公開しない。終局後公開は対局中の保護要件の緩和ではない。

サーバーとDBを判定の信頼境界とし、運用者・ログ・バックアップへのアクセスも限定する。状態と履歴の完全性、アカウントと参加権限、秘密鍵、長期間の再開に必要なデータも保護対象とする。

## 脅威と必須対策

| 脅威 | 経路・影響 | 必須対策 |
| --- | --- | --- |
| 敵駒情報漏洩 | API、HTML、JS、DOM属性、画像名、補助ラベル、LocalStorage、キャッシュ | 終局前の応答を閲覧者別の許可リストで生成し敵種類を送らない。見た目だけ隠す方式は禁止 |
| 棋譜・配信経由の漏洩 | 除去一覧、履歴、Realtime、通知、エクスポート | 完全棋譜は秘密領域へ保存し、終局前は許可された情報に制限する。生の秘密テーブルを配信しない |
| 終局偽装による漏洩 | クライアントの終了フラグ、別対局ID、公開APIの直接呼出し | 毎回サーバーで当該対局の終局状態と参加関係を確認。終局コミット前の全情報応答は禁止 |
| 不正着手・改ざん | 相手駒操作、経路違反、手番偽装、勝敗や状態の上書き | 認証主体・参加権限・状態・手番・駒所有者・合法性を正本で再検証し、戦闘はサーバー実行。状態の直接更新を禁止 |
| 二重着手・リプレイ | 二重タップ、複数端末、並列要求、応答消失後の再送 | state_versionと対局ロック、client_move_idの一意性・内容照合。状態・棋譜・PASS・再送記録を同一トランザクションで確定 |
| DB直接アクセス | 公開APIを迂回するREST・RPC・ビュー | RLSと最小権限。秘密の正本へブラウザ用ロールの汎用読み書きを許可しない。公開時も限定APIで必要情報だけ返す |
| READY競合 | LOCK後の配置変更、READY解除と開始の競合 | サーバーで直列化し、双方READY確認・LOCK・抽選・PLAYINGを原子的に処理。LOCK後の編集・解除を拒否 |
| ルール版改ざん | クライアントが有利な版を指定、改訂で既存対局を書き換え | 作成時ruleset_versionを固定し、判定は保存済み版を参照。進行中の変更は禁止し、旧版の解釈を保持 |
| 他対局へのアクセス | ID列挙、利用者ID偽装、招待URL流出 | 認証主体と参加関係を毎回照合。招待は参加枠取得に限定し、閲覧権限の代わりにしない |
| service role key等の流出 | フロント環境変数、成果物、Git履歴、ログ | サーバーの秘密管理にのみ置き、フロント・Gitに保存しない。漏洩時は失効・ローテーションとアクセス調査 |
| 再開不能 | 大量要求、データ消失、認証切れ | 要求量・サイズ制限、永続保存、バックアップ・復旧検証を設計。長期不在や認証切れで対局を終わらせない |

## 閲覧者別レスポンスの契約

終局前の認証済み参加者には、自軍種類・自軍除去駒を返せる。敵については位置・所属・生存／除去と合法的な着手・戦闘結果だけを返す。敵種類を直接表す内部ID、enum、並び順、画像参照、軍旗の有効駒種も返さない。識別子は種類から独立した不透明な値を使う。

秘密配置の途中情報を相手に送らず、READY等の進行に必要な状態だけを返す。エラー・デバッグ応答・ログ・レスポンス差分や合法手ヒントが非公開の判定理由を明かさないようにする。PASSは合法手なしのシステムイベントとして返せるが、その根拠となる敵種類を追加しない。

終局後公開APIは、認証→参加関係→コミット済み終局状態を確認し、許可された当該対局の全情報を返す。クライアントの申告、URLパラメーターやstate_versionの値だけでは公開を許可しない。終局処理がロールバックされた場合は全情報を送信しない。再送応答・再接続・棋譜・リプレイも同じ認可を適用する。

終局前の秘密をHTML・JavaScript・LocalStorage等へ埋め込まない。全盤面を先に端末へ送って後から表示を隠す方式は禁止。自軍情報と終局後に認可された全情報は表示可能。利用者別応答を共有キャッシュへ保存せず、ログアウト・アカウント切替時に前利用者の盤面や認証情報を残さない。終局後情報も認証を迂回する公開ファイルにしない。

## Supabase採用時の要件

- RLSを前提とする。行制御だけで列の秘匿を満たせると考えず、API応答自体から不要な秘密情報を除外する。
- 匿名・ブラウザ用認証ロールへ秘密の正本の汎用読み書きを許可しない。閲覧APIは参加者と対局状態に応じて情報を制限する。
- 更新は限定サーバー処理に集約する。関数の実行権限を限定し、権限昇格する関数では認証・参加確認、固定search_path等を設計する。
- RLSを迂回できるservice roleを使用する場合も、呼び出し利用者の権限・終局後公開条件を独立して検証する。
- ブラウザ向け公開接続キーは認可の代わりにならない。service role key等の秘密鍵と区別し、公開キーでの直接アクセスも検査する。
- Authの検証済み主体を利用する。認証トークン・Magic Link・招待トークンをログや解析サービスへ送らず、招待URLの参照元漏洩も抑制する。
- 状態の一意制約・ロック・トランザクションで並列処理を制御する。HQは1論理地点として重複占有を防ぎ、表示上のC/Dの違いで制約を迂回させない。

## 実装時の受入検証（今回は未実施）

1. プレイヤーA・B・第三者・未認証者の各立場で、開始前・PLAYING・終局後それぞれのAPI、DB直接アクセス、RPC、配信、履歴を検査する。終局前に敵種類がネットワーク・DOM等へ含まれないことを確認する。
2. 終局後は両参加者が全駒・LOCK時初期配置・完全棋譜・戦闘双方の種類を閲覧でき、第三者・未認証者・終局偽装要求には開示されないことを確認する。
3. 不正手番、所有者偽装、移動経路違反、古いstate_version、同一client_move_idの内容変更、ruleset_version改ざんを拒否し、盤面・履歴が変わらないことを確認する。
4. 並列着手、再送、応答消失、処理途中失敗で着手・PASS・カウンターが重複せず、状態と棋譜が一致することを確認する。READY解除とLOCKの競合も検査する。
5. 別端末・ブラウザ終了・再認証後も正しい手番・棋譜を復元でき、旧対局が固定ruleset_versionで解釈されることを確認する。
6. ビルド成果物・Git履歴の秘密鍵不在と、バックアップからの復旧を確認する。

これらは将来の受入条件であり、現時点で安全性を実証したものではない。
