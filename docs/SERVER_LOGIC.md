# サーバー処理設計

実装前の責務・処理順序の設計であり、コード・SQL・API実装ではない。ルールの正本は[GAME_RULES.md](GAME_RULES.md)、保護要件は[SECURITY.md](SECURITY.md)、既存方針は[ARCHITECTURE.md](ARCHITECTURE.md)。保存項目は[DATA_MODEL.md](DATA_MODEL.md)、画面は[USER_FLOW.md](USER_FLOW.md)、未承認案と実装順は[IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md)を参照する。

## 1. 信頼境界と実行単位

認証済みブラウザも信用しない。駒種類・手番・合法手・戦闘結果・勝敗・使用列・状態版を受け取っても、サーバーの正本を根拠に再検証する。認証主体から利用者を求め、要求の利用者IDから権限を作らない。

認証と入力サイズ等の検査を入口で行い、対局単位のロックと単一DBトランザクションで状態更新を直列化する設計を推奨する。純粋なルール処理をサーバーで呼び出す具体的方法はI2。通信途中に状態を複数回確定する構成は不可。ロック取得後の正本・state_versionで判断する。クライアントが事前に得た合法手一覧は着手許可証ではない。

参照応答も同一のコミット済みスナップショットを使い、盤面・手番・履歴末尾・state_versionをそろえる。初期配置、秘密駒、内部戦闘記録を汎用CRUDやRealtimeで流さない。閲覧者別応答は許可した項目を組み立て、余分な種類・内部理由を後から隠す方式にしない。

## 2. 操作の入出力と許可状態

以下は論理操作であり、URL・HTTP形式・型の確定ではない。使用列の具体的な項目名も今回は固定しない。

| 操作 | 主な入力 | 権限・状態 | 返す情報 |
| --- | --- | --- | --- |
| 対局作成 | 作成の重複防止情報（I3） | 認証済み | 対局ID、本人向け状態、招待リンク（X3） |
| 招待参加 | 招待トークン | 認証済み、空き枠 | 参加結果と本人向け配置画面の状態 |
| 配置保存 | 対局ID、基準state_version、駒IDと位置 | 本人、開始前・未READY | 自軍下書き、保存済み版、本人の配置エラー |
| READY / READY解除 | 対局ID、基準state_version | 本人、LOCK前 | READY状態または開始後の本人向け状態 |
| 着手 | 対局ID、駒ID、始点・終点、使用列、基準state_version、client_move_id | 本人の手番・PLAYING（成功再送は別扱い） | 受理結果、確定版、閲覧者別状態・イベント |
| 対局一覧・盤面・棋譜取得 | 対局ID等、履歴カーソル | 認証参加者 | 権限と対局状態に応じた情報のみ |
| 着手結果確認 | 対局ID、client_move_id | 元要求者かつ参加者 | 自分の要求の成功有無と公開可能な結果 |
| 自軍合法手取得 | 対局ID、駒ID、基準版 | 本人の手番・PLAYING | 移動先と必要な使用列。敵種類・戦闘予測なし |

自軍合法手は所有駒の能力、公開された占有・所属、経路から返せる範囲に限定する。敵の合法手一覧や、敵種類・軍旗性能を探索できる判定APIは設けない。棋譜はevent_seqでページングし、取得スナップショットの最終番号を上限にする案。新しい状態へ更新するときは上限も取り直す。

## 3. 対局作成と友人参加

### 作成

1. 認証主体と利用者レコードを確認する。期限切れ認証で作成しない。
2. 有効な公開ルール版をサーバー側で選び、ruleset_versionを固定する。対応処理のない版は作成不可。
3. 作成者をPlayer 1とする推奨案（X2）の承認後、P1を設定し、P2は空、WAITING、state_version=0、手数・非戦闘カウンター=0として対局を作る。
4. 招待を作り、生成した生トークンは応答時だけ使用し、保存はハッシュとする。対局と招待は同一トランザクションで確定する。
5. 使用する駒構成は各側16種類23枚としてサーバーが管理する。編集開始時に本人用の駒IDを用意し、相手向け応答に種類を載せない。参加待ち中の配置開始はX2の承認までは有効化しない。

作成の通信再試行で複数対局ができないよう、作成専用の重複防止情報を推奨する（I3）。client_move_idと用途を混ぜない。成功済み作成の再送では既存対局IDへ戻し、生トークンを保存していないため元リンクを復元できない場合はX3の再発行動線へ案内する案とする。新しい対局を作り直して代用しない。

### 参加

1. ログイン後に招待を照合し、存在・状態・失効・任意のexpires_at・参加枠を確認する。対局内容はまだ返さない。
2. 対局と招待を一貫した順序でロックし再検査する。同じ本人がP1/P2の両方になる参加を拒否する。
3. 未参加利用者1人をP2に設定し、招待をUSED、使用者・時刻を記録し、SETUPへ移す。state_versionを1増加させて原子的に確定する。
4. 並列参加は1人だけ成功させる。既に参加済みの同じ利用者の再アクセスは、枠を追加せず既存対局へ戻す。使用済みリンクを別利用者が使っても盤面を返さない。

招待期限は対局の手番期限ではない。参加後に招待が無効になっても認証参加者として再開可能。招待の期限・失効・再発行のUIはX3の未承認案。

## 4. 配置保存・確定・開始

配置途中保存の推奨案（X4）は、所有する23駒のうち未配置を許し、保存された非空位置の自陣・重複・駒所有者を検査する。禁止位置の説明は本人にのみ返す。不完全な下書きはREADYにできない。構成をクライアントが差し替えることは許可しない。

READY時と開始直前には次をすべて再検証する。

- 16種類23枚が正式構成と完全一致する。駒の欠落・重複・追加なし。
- 自陣23論理地点をすべて1枚ずつ埋め、盤外・他陣・二重占有なし。
- HQ-P1=C1+D1、HQ-P2=C8+D8を各1地点とし、アンカーを配置先にしない。
- 地雷・軍旗は自軍入口（P1：B4/E4、P2：B5/E5）不可。軍旗は最後列・HQ不可。地雷のHQは可。
- 対象配置が本人の最新保存版であり、対局未開始・未LOCKである。

READYは検証した配置リビジョンに対応付ける。READY中の編集はまず解除が必要。READY解除は未開始なら受理し、配置リビジョンとの現行READY対応を外す。両操作とも対局ロック内で再検査し版を更新する。

双方READYが同時に成立した状態をサーバーが確認したら、同じトランザクションで以下を行う。

1. 両配置を再検証しLOCK、初期配置スナップショットと現在駒を保存する。
2. 以降の編集・READY解除を禁止する。
3. サーバーの偏りのない乱数で一度だけ先手を選びfirst_playerへ保存する。
4. PLAYING、開始日時、暫定の手番を設定する。
5. 最初の合法手を調べる。片側だけ合法手なしなら自動PASS、双方なしなら即時引き分け。同じ開始処理の中で棋譜に記録する。
6. STARTと付随イベント、state_versionを保存して確定する。READY成立と開始を別々に外部公開しない。

READY解除が先にロックを取得すれば未READYとなり開始しない。開始が先なら後続の解除・編集を拒否し、最新状態へ誘導する。失敗時は抽選結果を含め未確定の変更を全てロールバックする。成功済みの開始を再実行・再抽選しない。READYにも現実時間の期限はない。

## 5. 着手検証・再送・原子的更新

### 再送と新規要求の区別

認証・参加権限を確認した後、対局ロック内で対局・利用者・client_move_idを照合する。同一IDで成功済みなら、正規化した全要求内容を比較する。同一内容は既存の成功を返し、異なる内容は拒否する。使用列や基準state_versionも比較対象に含める。

成功再送は現在の手番が変わっていたり終局していたりしても二重実行しない。古いstate_version拒否は未処理の新規着手に適用する。再送照合を手番・版の拒否より先に行うことで「成功したが応答だけ失った」状態を回復できる。成功結果の存在確認も本人に限定する。

### 未処理要求の検証

1. 対局がPLAYINGであり、現在の手番が認証利用者に対応するか。
2. 提示された基準state_versionがロック後の最新と一致するか。
3. 駒が同じ対局に属する生存中の本人所有駒で、申告始点に実在するか。
4. 目的地点が有効な論理地点で、始点と異なり、味方占有でないか。
5. 真の種類と所有者方向から移動能力・距離・直線経路が合法か。軍旗・地雷の移動を拒否する。
6. 中間地点の駒による妨害を種類ごとに検査する。工兵と前方2マスは味方も敵も通過不可。飛行機は味方だけ通過可。
7. 境界越えは飛行機を除きB4↔B5、E4↔E5のみか。長距離移動でも途中の境界を検査する。
8. HQは各1論理地点で始点か終点だけか。接する各HQにつき1アンカーを使い、同一HQ内の切替・中継・方向転換がないか。
9. 飛行機のHQ間直接移動ではC/Dの指定を必須とし、両端同列、中間C2〜C7またはD2〜D7に敵なし、到着HQに味方なしを検査する。両端合計2アンカーは合法。列を黙って差し替えない。
10. 目的地点の敵がいれば戦闘直前状態から戦闘を一意に算出できるか。クライアントの結果や勝敗は採用しない。

すべての幾何はPlayer 1正規座標を使用し、P1前方row+1、P2前方row-1。HQ隣接はP1がB1/C2/D2/E1、P2がB8/C7/D7/E8。画面の回転は判定に影響させない。HQで止まった後の別の手では別ポートから退出できる。以前の着手列を現在の移動制約にしない。

### 戦闘からコミットまで

軍旗の有効駒種を、戦闘直前の所有者から見た直後の味方駒から計算する。C2/D2のP1軍旗はHQ-P1、C7/D7のP2軍旗はHQ-P2へ対応する。味方がなければ軍旗敗北。同じ有効駒種は相打ち。種類継承によって軍旗の移動・占領資格を増やさない。

GAME_RULES.mdの勝敗表をruleset_versionに対応させて参照する。独自の優先順位で表を作り直さない。攻撃側勝利は攻撃駒を目的地点へ移し防御駒を除去、防御側勝利は攻撃駒だけ除去、相打ちは双方除去。地雷は飛行機・工兵には一方的に除去され他とは相打ち。軍旗の後方駒自体はこの戦闘で除去しない。

以下を単一トランザクション内で順に実行し、途中の盤面を公開しない。

1. 移動・戦闘を完了。受理着手番号を1増加し、非戦闘ならカウンター+1、戦闘なら0にする。
2. 更新後の盤面をトランザクション内で確定する。
3. 占領資格のある駒が敵HQへ生存停止したら着手側勝利。飛行機は資格なし。
4. 占領可能駒の残存数を判定。双方0なら引き分け、片側0なら反対側勝利。
5. 双方の合法手を検査。双方なしなら引き分け。次手番候補だけになければ自動PASSの必要を記録する。
6. 未終局で非戦闘カウンター50なら引き分け。
7. 未終局なら次手番を設定し、必要ならAUTO_PASSで相手へ送る。50手等で終局したら不要なPASSを生成しない。
8. 駒・結果・手番・カウンター、MOVEと付随するPASS/END、使用列、成功再送記録を保存し、state_versionを1増加してコミットする。

最初に成立した終局理由で打ち切り、FINISHED・勝者・理由・終局日時を保存しcurrent_turnを空にする。飛行機の敵HQ停止だけでは勝利にならないが、最後の占領可能駒を除去した場合は既存条件どおり勝利し得る。

## 6. 合法手なしと自動PASS

任意のパス要求は設けない。合法手がない手番側は敗北にせずサーバーが手番を送る。自動PASSはシステムイベントであり、move_countとnoncombat_countは加算もリセットもしない。付随する着手または開始のコミットに含め、独立したプレイヤー着手IDを発行しない。

両者なしは即時引き分けでPASSを往復させない。片側だけなしなら1回送った先に合法手があるため無限ループしない。存在判定は各所有側の正本を内部だけで評価し、相手の合法手一覧・種類を応答に出さない。相手PASS後は同じプレイヤーが続けて手番を持つことがある。

## 7. 失敗・競合・再接続

| 状況 | サーバー動作 | 利用者向けの扱い |
| --- | --- | --- |
| 未認証・非参加者 | 状態・秘密を返さない | ログインまたはアクセス不可 |
| 古い版、手番変更、LOCK済み | 新規要求を拒否し変更なし | 最新状態を取り直す |
| 不正駒・経路・使用列 | 変更なし。内部理由を秘密なしに分類 | 操作不可。敵種類や戦闘予測を含めない |
| 同じID・異なる内容 | 拒否 | 再送対象の不一致として扱う |
| ロック待ち・一時障害 | 未コミットなら全変更なし | 同じ要求ID・内容で結果確認／再試行 |
| コミット後の応答消失 | 成功記録は保持 | 同じIDの成功確認と最新状態取得 |

状態照会で未処理に見えても元要求が処理中の可能性がある。新IDで同じ手を再送せず、同一IDで確認する。ブラウザに保留IDが残っていれば再利用し、消失していてもサーバーの本人向け直近着手・確定版から復元する。処理中の同版要求はロック・版検査により二重受理しない。確認前に過去の着手を自動で新規送信しない。

## 8. 閲覧者別情報と長期継続

対局前・中は自軍種類、自軍除去種類、敵不明駒、許可された移動・戦闘結果・使用列・PASSだけを返す。合法的な特殊移動からの推測は許容するが、真の種類や軍旗の内部性能を直接返さない。自軍情報はP1/P2で同じ方式で生成する。

終局コミット後のみ、認証済みの当該参加者へ全駒種類、LOCK時初期配置、完全棋譜、各戦闘双方の種類を公開する。Auth秘密や招待ハッシュ等は終局でも非公開。古い再送結果や履歴ページにも毎回同じ認可を課す。

セッション切れや数か月の不在で対局を消さず、再認証後に最新state_version、棋譜、現在の手番から再開する。時刻は並び順の正本にせずevent_seqを使う。バックアップ復旧、旧ruleset_version維持はDATA_MODEL.mdに従う。通知・Realtimeは補助で、状態更新の成功条件にしない。

## 9. 設計の検証境界

自動検証対象は、正式勝敗表、合法手・回転対称性、READY競合、同一ID並列送信、異内容再送、古い版、戦闘後の終局優先順位、PASSの一回性、コミット途中失敗、応答消失、参照スナップショットの一貫性、全情報の認可境界。具体的な段階別確認はIMPLEMENTATION_PLAN.mdにまとめる。現時点で実装や動作検証を行ったという意味ではない。
