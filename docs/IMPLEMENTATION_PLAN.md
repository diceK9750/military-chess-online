## 1. 共通の進め方

各段階の完了条件を満たしてから次へ進む。自動化できる規則・データ・権限・通信障害の確認を自動化し、人間は視認性・指の操作感・実機固有の問題に集中する。画面幅の自動検査を実スマートフォン検証の代わりとして報告しない。

全段階で、16種類23枚、各23配置地点、HQ各1論理地点・最大1駒、突破口B4↔B5/E4↔E5、既存勝敗表、終局順序を保持する。ルール変更はこの実装計画から行わない。実装中に未定義を発見したら、正式仕様の更新を承認してから進める。

初期配置・対局画面の広い表示では、左ルール・中央盤面・右ルールの3列を対称に配置し、十分な幅と高さがあればページとルール欄をスクロールさせない。画面高に合わせて盤面を調整し、狭い場合は左右欄を隠して盤面を中央に置く。強弱の表示は共通の駒定義・戦闘判定から生成し、指定された複数画面サイズで配置・対局の両方を検証する。

将来のオンライン対人戦では、対局中の敵種類を通信で送らず、手番・種類・合法手・勝敗・使用列をサーバーで再検証する。client_move_id、state_version、ruleset_versionの既存契約をオンラインの全層で共有する。対CPUローカル対局では、CPU思考へ渡す情報をCPUの可視情報に限定する。ローカルの完全盤面は端末上に存在するため、オンラインの秘密保護を実証したものとは扱わない。

## 4. 第3段階：CPU対戦（初期実装）

| 観点 | 内容 |
| --- | --- |
| 目的 | 1人で正式規則による対CPU戦を始め、終局まで進められるようにする |
| 作るもの | かんたん・ふつうの選択、CPUから見える情報への変換、合法なCPU配置、先手抽選、CPU自動着手、対CPU画面と結果表示 |
| 作らないもの | 認証、招待、通信、DB、サーバー処理、実対局の再読込後復元 |
| 完了条件 | 利用者の配置確定からCPUの自動着手・終局まで進行し、CPUは合法手のみ選ぶ。人間とCPUで同じ規則処理を使う |
| 必要な自動テスト | 可視情報への変換、敵の秘密駒種変更に対する判断不変性、両難易度、合法配置・禁止地点、固定乱数種、P1/P2、手番・PASS・終局、画面操作 |
| 人間の確認 | スマートフォン相当の縦持ちとPCで配置・着手・結果の視認性を確認。実機確認は第6段階 |

CPU思考関数の入力は自軍の駒種・位置、敵の位置、公開履歴・戦闘結果、現在手番、合法手に限定する。相手の未公開駒種や秘密の初期配置を渡さない。かんたんは合法手から均等ランダムで選び、ふつうは公開情報に基づく評価値で選ぶ。評価値と重みは調整しやすい一か所に置く。固定乱数種で結果を再現できるようにする。CPU配置の戦略的な偏りは配置生成の選択であり、正式な配置制約の追加ではない。

CPU手番は人間の確定着手後、共通規則で盤面・終局を確定してから処理する。CPUは可視情報で選んだ手を共通の着手関数へ渡し、別の戦闘判定を持たない。CPU思考中は人間の二重操作を止める。対局本体はこの段階では再読込で失われる。

| 必要な自動テスト | 保存形式版・ルール版、破損・不正状態、暗号化往復・改ざん検出、終局状態、CPU情報境界、React画面とモバイル/PCブラウザ操作 |

保存形式版とruleset_versionを区別する。CPUの独立した推理状態は現在存在せず、乱数種と履歴を保存する。ブラウザ保存には完全盤面が平文で含まれ、端末所有者に対する対局秘密の保証とは扱わない。ファイルはWeb CryptoによるPBKDF2-SHA-256とAES-256-GCMで暗号化し、復号前メタデータから駒情報を除く。読み込みでは初期配置から全着手をルール再生して整合性を確認する。
