# 初期アーキテクチャ案

本書はコードを伴わない初期案。[GAME_RULES.md](GAME_RULES.md)がルールの基準、[SECURITY.md](SECURITY.md)が必須の保護要件。技術選択は再検討可能だが、秘密情報をクライアントへ渡さないこととサーバーによる原子的な判定は必須とする。

## 構成候補

| 構成要素 | 初期案と役割 |
| --- | --- |
| フロントエンド | 静的Webアプリ。盤面表示、タップ入力、閲覧者別状態の取得。フレームワーク・言語・ビルド方式は未選定 |
| GitHub Pages | 静的フロントエンドの公開先第一候補。秘密情報やサーバー処理を配置しない。今回は設定しない |
| Supabase Auth | メールMagic Linkを第一候補とする。長期利用・機種変更後も同じアカウントで再開。最終方式はバックエンド設計時に再検討 |
| Supabase DB | PostgreSQLに対局・秘密配置・着手履歴を保存。RLSと権限を前提にする |
| サーバー側ゲーム処理 | 認証済みAPIから呼ぶDBトランザクションを候補とする。Edge Functionsを入口にするかDB関数へ直接要求するかは未定 |

GitHub Pagesから認証・APIへ接続する。認証のリダイレクトURL、メール運用、ホスティングパスは導入時に確定する。認証セッションが切れても対局を削除・終了せず、再認証後に復帰させる。

## スマートフォン優先のUI要件

縦持ちで基本操作が完結し、原則として横スクロールを生じさせない。タップ操作を中心に駒・ボタンの十分な大きさを確保する。自軍と敵軍を直感的に識別できる表示にし、敵種類を画像・ラベル・補助情報にも出さない。PCブラウザにも対応する。

再開画面では現在の手番、対局状態、最後に起きた着手・戦闘結果を、許可された情報のみで表示する。通知や相手のオンライン状態がなくても対局を進められることを必須とする。

## データモデル案

物理スキーマ・列名は未確定。以下は責務の分割であり、公開APIの生のテーブル一覧ではない。

| データ | 内容と公開範囲 |
| --- | --- |
| 対局 | 参加者、状態、手番、version、ルール版、非戦闘手数、結果。参加者向けにも必要な項目だけ返す |
| 配置・駒の正本 | 所有者、種類、位置、生存状態、配置確定状態。サーバー専用の秘密領域 |
| 着手履歴 | 手番号、前後version、操作、結果。秘密の判定記録を持つ場合はサーバー専用に分離する |
| 閲覧者別状態・履歴 | 自軍の種類と除去駒、敵の不明駒、公開可能な着手と結果。認証利用者に合わせてサーバーで生成 |
| 招待 | 対局、発行者、トークンのハッシュ、使用状態等。参加権限と分離して扱う |
| 再送管理 | 対局・利用者・request_id、要求内容との対応、処理結果。二重処理防止に利用 |

状態は「招待待ち → 配置中 → 対局中 → 終了」を候補とし、参加枠は2名に制限する。配置の再編集可否はGAME_RULES.mdのU5に従い決定する。先手抽選は双方の配置完了と同じ排他制御下で一度だけ行い、結果を保存する。サーバーで偏りのない乱数を使用する。

## 1手の原子的な処理

1. クライアントは対局ID、着手元・先、expected_version、一意なrequest_idを送る。種類・戦闘結果・手番はクライアントの申告から採用しない。
2. サーバーは認証主体から参加者を特定する。対局・利用者ごとの再送記録を確認し、同一IDで内容の異なる要求は拒否する。
3. DBトランザクションで対象対局をロックし、最新version、対局状態、手番、駒所有者、全移動経路・停止位置を正本から検証する。
4. サーバーで戦闘を判定し、盤面、除去駒、連続非戦闘手数、勝敗、次手番を更新する。終局の未確定分岐はGAME_RULES.mdのU3・U4を解消してから実装する。
5. 状態、履歴、再送記録を同一トランザクションで保存し、versionを1増加させてコミットする。失敗時は全体をロールバックする。
6. コミット後、要求者に許可された状態・結果だけを返す。

expected_versionが古い新規要求は拒否し、最新状態の再取得を促す。すでに成功した同一要求の再送では着手を再実行しない。再送応答も閲覧者別に制限し、状態がその後進んでいれば最新取得へ誘導する。HTTPタイムアウトは未処理を意味しないので、同じrequest_idで結果確認できる設計とする。

配置・参加・対局開始などの状態変更も原子的に行い、versionを更新する案とする。このためversionと手番号は別管理とする。1手ごとに別々のHTTP書き込みを重ねるだけの実装は不可。

## 非同期対局・棋譜・再接続

正本はDBに置き、ブラウザのメモリやローカル保存は再開の必須条件にしない。再ログイン時は参加対局一覧と最新の閲覧者別盤面・version・履歴を取得する。ネットワーク復帰後も再取得し、古い盤面から自動着手しない。

全受理着手を順序付きで永続保存し、履歴と盤面が同じコミットを表すことを保証する。棋譜閲覧・将来のリプレイ・エクスポートにも同じ秘匿ルールを適用する。相手の操作を検出する方法は画面復帰時の取得と手動更新を基本案とする。Realtimeは任意の補助であり、使う場合も秘密のテーブル変更を直接配信しない。

現実時間の放置を理由に対局データを消したり終局させたりしない。数か月後の再開に必要な保存・バックアップ・復旧・スキーマ移行方針は運用設計時に具体化する。サービス停止時にも無期限で利用できるという保証はここでは行わない。既存対局に新ルールを暗黙適用しないため、対局ごとにルール版を保存する案とする。

## 招待URL・将来の通知

招待URLは十分な乱数を持つトークンを含む案とする。ログイン後にサーバーで検証し、空き参加枠へ一度だけ原子的に参加させる。URLを知っているだけで盤面・秘密情報を閲覧できる設計にはしない。参加後の対局アクセスは利用者IDとの対応で判断する。トークンの有効期限・失効方法は未定であり、招待の期限とゲームの手番期限を混同しない。

メールやPushによる手番通知は将来機能。通知なしで全対局を継続でき、通知失敗で着手を巻き戻さない。導入する場合はコミット後のイベントを送信キューで処理し、重複送信を抑制する。通知には敵種類・秘密配置を含めず、受信設定や方式はその工程で決める。

## 実装への入口

まずGAME_RULES.mdのU1〜U5を確定する。その後に認証方式・物理スキーマ・API契約・RLSとサーバー実行権限を具体化する。本書の候補だけを根拠に外部サービスを作成したり、フロントエンドへ秘密鍵を置いたりしない。
