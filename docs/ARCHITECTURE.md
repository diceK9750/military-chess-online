# 初期アーキテクチャと正式方針

初回公開は対CPU戦のみを目標とし、オンライン対人戦は将来拡張として保持する。[GAME_RULES.md](GAME_RULES.md)がルールの正本、[SECURITY.md](SECURITY.md)は将来のオンライン対人戦でも守る保護要件。通信・一貫性・READY・終局後公開のオンライン方針は削除せず、対CPU戦のローカル構成と区別する。

## 初回公開目標：対CPU戦

- React / TypeScript / Viteの静的アプリを1人が操作し、CPUを相手に同じv0.2ルール処理を使う。公開先はGitHub Pages。
- Player 1を利用者、Player 2をCPUとする画面上の割当。CPU配置は正式な23枚・23地点の制約で自動生成する。先手は両配置確定後にローカルで抽選し、ルール計算関数へ注入する。将来のオンライン対人戦では既存の作成者=P1・サーバー抽選方針を維持する。
- CPU思考は完全な`GameState`を受け取らない。変換器がCPU自軍の種類・位置、相手の位置と所属、公開着手・戦闘結果、合法手、手番だけを渡す。相手の未公開種類・初期配置の種類・駒ID・完全な内部戦闘情報を渡さない。`かんたん`は合法手集合から選び、`ふつう`は公開情報だけで局面を評価する。乱数種を固定した選択と配置は再現可能にする。
- 人間・CPUの着手は同じ合法手・戦闘・終局処理を使用する。CPU手番中は操作を受け付けない。開発用の検証画面は別入口として保持する。
- 第4段階で対CPU対局の自動保存・パスワード付き書き出し・読み込みを追加する。配置中は難易度・乱数種・自軍配置を準備中キーへ保存し、確定後の開始・着手・PASS・終局は専用の対局キーへ整合した状態で保存する。再読込では初期配置から棋譜を共通ルールで再生して保存値と照合する。長期保管・端末移行は`.mcsave`ファイルを使う。保存形式版とルール版は別に管理し、CPU難易度・乱数種・状態版を含める。端末上のローカル対局だけを扱い、サーバーは不要。
- ブラウザ内の完全盤面は端末所有者が開発者ツール等で読める。対CPU戦の公平性は**CPU思考への入力制限**で担保し、オンライン対人戦の秘密保護や改ざん耐性とは区別する。

## Step 12：三次元を正式な主操作面へ統一

GameStateとLocalGameの操作制御が正本。三次元は既存正式ゲーム処理を操作する主画面であり、合法手・戦闘・勝敗・CPU・保存処理を持たない。selected、pending、lane、executeはLocalGameの1組だけを使う。三次元のRaycasterはSiteまたはC/D列のみを通知し、既存selectと列選択へ接続する。補助UIの確認・選択解除・列選択も同じ処理へ接続し、独自のルール判定を持たない。

src/battlefield3d/state.tsの変換器だけがGameStateを受け、BattlefieldViewStateへ許可項目をコピーする。生存駒のowner・position・unknown、自軍／終局後のtype、閲覧側、手数、終局フラグ、公開済みの直前着手地点と戦闘地点を含む。追加の操作情報はselectedSite、legalTargets、pendingSite、laneCandidates、selectedLane、interactionEnabledに限定し、配列もコピーする。対局中の敵type・内部ID・元オブジェクト参照は渡さず、地点順も固定する。MeshのuserDataにはSiteかlaneだけを置く。端末内の完全盤面を秘匿するオンライン用保護とは区別する。

Step 12BではCpuSetupも共有BattlefieldViewを使用する。配置用変換器toSetupBattlefieldViewは自軍配置配列だけを受け、自軍の種類・地点と選択・交換可能地点をコピーする。敵駒は入力されても除外し、IDや元配列参照を描画器へ渡さない。CPU配置の生成は従来どおり配置確定時に行う。交換可能地点は既存exchange・validatePlacement・territoryから求め、三次元はSiteを通知するだけとする。交換・8種類の陣形変更はいずれも検証済み配置を既存の下書き／準備中保存へ反映する。陣形選択UI自体は保存項目に追加せず、難易度・乱数種・配置の保存形式を維持する。

Three.jsと同梱OrbitControlsはタイトル・難易度では読み込まず、配置または対局コンポーネントのマウント時にdynamic importする。通常の初期配置・CPU対局・続きから・終局は中央の三次元戦場と操作補助UIだけを表示する。広い画面では左右ルールも置き、狭い画面では縦スクロールを許容する。二次元BoardはWebGL2非対応・読込失敗・コンテキスト喪失時の緊急フォールバックだけとし、配置交換と対局を継続できる。開発用Setupだけは二次元Boardを常時使用する。モーダル・開閉ボタンは廃止した。

配置・対局に共通のカメラプリセットは全景・真上・自軍正面・選択中の駒。真上でも描画と入力は同じ三次元シーンを使う。選択駒視点は選択地点へ追従し、画面サイズ変更時は現在のプリセットを維持する。カメラ操作は配置・着手・保存を変更しない。

通常のRaycaster入力とOrbitControlsを共存させ、開始点から6 CSS pxを超える移動、複数指、pointercancel、領域外のリリースは選択にしない。CPU手番・終局・移動演出中は三次元入力を受け付けない。演出中は描画器からのbusy通知で補助UIと共通入力も抑止する。通知だけの再描画が演出を取り消さないよう表示状態をメモ化する。正式な手番再検証と二重確定防止は既存LocalGameで行う。三次元で予定手を選んだ際は確認欄へ自動スクロールせず、再タップ操作を継続できる。

確定した公開表示状態の差分を短時間で補間する（Step 13では220〜340 ms、未公開敵は一律300 ms）。公開済み飛行機は上昇、騎兵は突進、タンクは緩急、工兵は直線の移動とする。除去された攻撃駒は直前の公開情報による簡素な駒を目的地へ動かして消す。次の状態が来たら古い移動演出を打ち切り最新状態を優先し、CPU応手を待たせたり独自に結果を計算したりしない。動きを減らすOS設定では移動演出を省く。

パン無効・仰角／距離制限を維持する。カメラ操作、状態変更、短い演出中だけ描画し、終了後は停止する。画素比上限は狭幅1.25、その他1.5。対局画面を離れるとRAF、Observer、操作リスナー、ジオメトリ、マテリアル、文字テクスチャ、WebGL資源を破棄する。読込失敗・WebGL2非対応・コンテキスト喪失は三次元領域内に案内し、二次元対局と保存を継続できる。

キャラクターは共有ジオメトリの頭・胴・手足・装備で構成し、名称はカメラへ向く横長ラベルにする。未公開敵は同一形状・寸法・材質・装飾・「？」表示。種類別装備の分岐は公開済みtypeを持つ駒だけに適用する。内部IDは描画器へ渡さない。終局後は同じ変換境界で全種類を許可する。

BGMはHTMLAudioElementで1曲をループ再生する。初期OFF、srcは最初の明示操作まで未設定。保存済みONも再読み込み後の自動再生を許可しない。音量・ON設定は専用キー military-chess-audio-v1 に保存し、対局形式・暗号化には含めない。保存領域・音源・再生拒否のエラーは対局進行に影響させない。アプリ終了時に停止する。同一公開元からMP3を配信し、外部音楽サービスへの実行時通信は不要。音源とCC BY 4.0の出典・表示要件はREADMEと同梱CREDITSを参照。

## Step 13：軍議盤と公開情報の戦術解析

### 描画バックエンドと伝統的な駒

`backend.ts`がWebGPU優先の非同期初期化と既存WebGL2描画器を共通インターフェースで包む。アダプターを確認してから`three/webgpu`を遅延読込し、`init()`とWebGPUバックエンドの確認に成功した場合だけ使用する。初期化失敗時はGPU資源を破棄して新しいcanvasでWebGL2を開始する。稼働中のGPUデバイス喪失・描画エラーはGLで一度再作成し、それも失敗したら既存Boardへ切り替える。GPUを使用できるだけで必須表示を変えず、特殊シェーダーやTSLは今回導入しない。[Three.js公式のWebGPURenderer説明](https://threejs.org/manual/pages/webgpurenderer)を参照。

木色の五角形台座に名称を載せ、共有ジオメトリの兵士へ種類別装備を加える。将官・士官は徽章の数と幅、飛行機は翼、工兵は工具、騎兵は馬、タンクは装甲、旗は旗竿で区別する。墨色グリッド、木の外枠、古地図色の地面、既存の橋・本陣を組み合わせる。名称ラベルはカメラへ向き、距離で0.85〜1.12倍に調整する。未公開敵には同じ形・高さ・色・装備・「？」だけを渡す。種類別の描画・移動分岐へ秘密typeを渡さない。

### AI参謀の情報境界

`tacticalView`を完全盤面との唯一の接点とし、既存`observeForCpu`から相手typeと全内部IDを除き、自軍既知種類・自軍初期配置・地点・公開履歴・合法手だけをコピーする。推論・表示・公開理由・解析オーバーレイはこの情報で動く。生成AI・外部API・追加通信を使用しない。対CPU戦のブラウザ内完全盤面という制約は従来どおりで、オンラインの秘密保護を証明するものではない。

CPUの共通`evaluateMove`は既存の採点順序と値を維持し、`terms`とその合計を返す。`chooseCpuMove`の乱数・同点・難易度処理は変えない。Step 12Bから凍結した独立評価関数と固定seedの生成対局で、各合法手の点数と実際の選択を照合する。自軍の戦術候補は同じ評価器で最大3件を示し、自動着手しない。

CPU自身の既知種類に由来するボーナス・戦力リスク・総合点を対戦相手へ出すと種類が漏れる。そのためCPU説明は実採点のうち、本陣距離、公開戦闘機会、本陣周辺の敵数、往復、50手回避だけを公開履歴から再構築する。表示は「公開要素小計」であり、秘密を含む総合点として表示しない。自軍候補には自軍が知る全採点を使用できる。

未知敵候補は地点をキーにした匿名の移動追跡で復元する。初期配置の公開制約、公開移動と占有状態を正式`moveError`へ渡し、候補を除外する。戦闘では自軍初期配置から追跡した既知種類と公開勝敗を正式`combat`で照合する。軍旗の直後駒も候補集合として扱う。内部駒ID・敵真type・秘密配置・確率モデルは使わない。未追跡の情報は保守的に候補へ残し、候補の全体枚数からの推定は行わない。証拠は直近2件を示す。

初期OFFの設定を対局データとは別の`military-chess-intelligence-v1`へ保存する。ON時だけ最大3経路・未知駒の候補数リングと公開戦況を表示し、展開UIは縦スクロールを許容する。表示を計算するための連続描画は行わない。

### 戦闘演出・効果音・戦史再現

戦闘地点と公開勝敗だけから800 msの墨・光粒子を作る。最近3秒以内の手動カメラ操作では寄らず、操作がなければ一時的に寄って元の位置と注視点へ戻る。手数スライダーによる中断時も復帰し、演出中の手動変更は優先する。OSの`prefers-reduced-motion: reduce`では移動・戦闘演出を省く。移動busyと戦闘粒子の寿命を分離し、CPUの正式処理を演出で遅延させない。画素比の上限は従来どおり、粒子数は狭幅6・その他12で固定し、操作中の頻繁な品質変更はしない。

効果音は明示ON操作で初めてAudioContextを作成・再開し、選択・移動・解析・戦闘・終局の短い合成音を小さな音量で鳴らす。OFFでsuspend、終了でclose、音源ノードは終了後に切り離す。音の失敗は対局を止めない。BGM素材、設定、クレジットは変更せず、ダッキングは未導入。効果音は再読込ごとにOFFとなる。

終局後だけ`chronicleFrames`が保存済み初期配置とMOVEを`startGame`／`applyMove`へ通し、全フレームを作る。最終局面・イベントが保存局面と完全一致しなければ再生を拒否する。終局元対局を確認した表示変換で過去フレームの全種類を表示し、途中局面の結果や保存データは変更しない。Chronicleは独立した再生インデックス・タイマーを持ち、再生／停止・前後・手数指定・0.5/1/2倍速を提供する。C/D列やAUTO_PASS・ENDの扱いは正式エンジンに任せ、独自ルールを作らない。

## 将来のオンライン対人戦拡張

以下の既存設計は第7段階以降の参照仕様として保持する。盤面座標・HQ等の共通ルールは対CPU戦にも適用する。

### 構成候補

| 構成要素 | 初期案と役割 |
| --- | --- |
| フロントエンド | React / TypeScript / Viteを正式採用。npmで依存管理。現在は対CPU画面と開発用画面。オンライン拡張では閲覧者別状態の表示とタップ入力 |
| GitHub Pages | フロントエンド公開先の第一候補。秘密情報やサーバー処理を配置しない。今回は設定しない |
| Supabase Auth | メールMagic Linkを正式ログインの第一方式として承認。長期利用・機種変更後も同じアカウントで再開。サービス接続は未実装 |

| サーバー側ゲーム処理 | 認証済みAPIから呼ぶDBトランザクションを候補とする。Edge Functionsを入口にするかDB関数へ直接要求するかは未定 |

認証のリダイレクトURL・メール運用・公開パスは導入時に確定する。セッションが切れても対局を終了・削除せず、再認証後に復帰できるようにする。ブラウザのローカルデータだけを本人確認・状態保存の根拠にしない。

### スマートフォン優先のUI要件

縦持ちで基本操作が完結し、原則として横スクロールを発生させない。タップ中心に、駒・ボタンの十分な大きさを確保する。自軍と敵軍を直感的に識別でき、対局中は敵種類を画像・ラベル・補助情報にも漏らさない。PCブラウザにも対応する。

初期配置・対局画面は盤面を利用領域の水平中央へ置き、十分な幅と高さがあるときだけ「左ルール｜中央盤面｜右ルール」の3列で表示する。1画面モードでは盤面を残余高に収まる最大寸法にし、左右の欄とページに縦スクロールを出さない。ルール表示のため盤面や操作を必要以上に縮小せず、内容は初見向け要点へ絞る。強弱表示は共通の駒定義・戦闘判定から生成する。狭い画面では左右欄を隠し、盤面を中央に置いて既存の「遊び方」を利用できるようにする。

再開画面では現在の手番、状態、前回の着手・戦闘・自動PASSを許可された情報だけで表示する。終局後は参加者向けの全情報閲覧へ切り替えられる。通知や同時接続を再開・対局進行の条件にしない。

### 盤面表現の正式方針

正規座標はPlayer 1視点のA〜F・1〜8で固定する。Player 1はrows 1〜4で前方row+1、Player 2はrows 5〜8で前方row-1。境界を越える通常の接続はB4 <-> B5、E4 <-> E5のみで、飛行機の例外はルール正本に従う。

HQ-P1はC1+D1、HQ-P2はC8+D8を占める各1論理地点として保存し、物理マスごとに別の駒を保存しない。各陣営23地点・23枚を満たす制約を設計する。表示を180度回転しても保存座標は変えず、入力を正規座標へ戻して送信する。HQのタップ領域は同一の論理地点へ対応させる。

HQへ出入りする移動経路・距離・隣接と軍旗の直後対応はGAME_RULES.mdのR1を正本とする。HQ-P1のC1-anchor/D1-anchor、HQ-P2のC8-anchor/D8-anchorは幾何計算専用で、配置・占有・保存する独立地点にはしない。1マス隣接はHQ-P1がB1/C2/D2/E1、HQ-P2がB8/C7/D7/E8で、接続は双方向。

サーバーは着手元・目的論理地点と、HQ間直接移動では選択した列から、接する各HQにつき1つのアンカーと直線経路を求め、所有者の方向、距離、中間駒、突破口、停止条件を検証する。通常地点とHQ間は1アンカー、HQ間は両端合計2アンカーとなる。HQは経路の始点か終点に限定し、同じHQ内のアンカー切替・HQ通過・列変更・方向転換を拒否する。工兵と飛行機の経路制約はそれぞれの既存能力に従う。軍旗の後方物理座標がHQ領域なら論理HQへ対応させ、正本の所有者と戦闘性能を参照する。

HQで手を終了した駒の位置はHQだけを保存し、進入ポートを次の手の制約となる永続状態にしない。後の手は新しい始点として合法なrayを選択できる。表示回転やクライアントが申告したアンカーを判定の根拠にせず、Player 1/Player 2の180度対称性を保つ。

飛行機のHQ間直接移動では、選択したC列またはD列を着手情報として保持する。両端は同じ列のアンカーとし、サーバーは選択列の直線経路、途中の敵味方駒の飛越、到着HQの占有と戦闘を再検証する。途中の駒は経路を塞がず、戦闘対象にもならない。選択された列を別の列へ黙って差し替えない。飛行機以外へ境界越えを拡張しない。

使用列はサーバー側再検証、対局履歴、対局再生、通信再送時の同一着手判定、不正経路検出に必要な情報とする。同じclient_move_idで使用列が異なる要求は、既存の「同じIDで内容が異なる要求」として拒否する。受理した使用列を着手・棋譜・再送記録の同じトランザクションで保存し、再生時に別経路を推測しない。使用列の履歴保存は進入ポートを駒の永続的な移動制約にするものではない。変数名・データ形式・通信形式は今回固定しない。

### データの責務と正式な識別子

物理スキーマは未確定だが、以下の3識別子の意味は正式方針とする。

- `client_move_id`：各着手に一意に付ける再送識別子。同じ着手の再送は同じ値を使う。
- `state_version`：ゲーム状態の単調増加する版。新規着手は基準とした版を提示し、最新と一致しなければ拒否する。
- `ruleset_version`：対局作成時に固定保存するルール版。進行中に変更せず、改訂後も既存対局は作成時の版で解釈する。履歴の解釈にも同じ版を使用する。

| データ | 内容・責務 |
| --- | --- |
| 対局 | 参加者、状態、手番、state_version、ruleset_version、非戦闘カウンター、結果 |
| 駒の正本 | 所有者、種類、論理地点、生存状態。サーバー専用領域 |
| 配置 | 編集中配置、READY状態、LOCKした初期配置。初期配置は終局後公開に備えて保持 |
| 完全棋譜 | 全受理着手と戦闘双方の実駒種、軍旗の有効駒種等の判定情報、自動PASSイベントを順序付きで保持 |
| 閲覧者別応答 | 対局中は自軍種類と敵不明駒・許可された結果、終局後は認証済み参加者だけに全情報 |
| 再送管理 | 対局・利用者・client_move_idと要求内容・処理結果の対応 |
| 招待 | 発行者、対局、トークンのハッシュ、使用状態等 |

補足：再送識別子は対局・認証主体との対応も照合して他利用者の結果を返さない。状態の版、プレイヤー着手の手番号、PASSを含むイベント順序は別概念とする。完全棋譜を終局時に推測で復元せず、対局中は秘密領域に保存する。ルール版の具体的な識別形式は詳細設計で決める。

### READYから開始まで

開始前は編集可能で、配置確定するとREADYになる。READY状態では解除してから再編集する。READY解除と開始処理を対局単位で直列化する。

サーバーが双方READYを確認したら、両配置の検証・LOCK、以後の編集とREADY解除の禁止、偏りのない先手抽選、PLAYINGへの変更を同じトランザクションで行う。LOCKした初期配置を保存し、開始時の合法手も検査する。合法手なしならルール正本どおり自動PASSまたは双方合法手なしの引き分けを処理する。途中の開始状態は外部公開しない。配置・READYに現実時間の期限を設けない。

### 1手の原子的な処理

1. クライアントは対局ID、着手元・目的論理地点、基準のstate_version、client_move_idを送る。飛行機のHQ間直接移動では使用するC列またはD列も着手情報として伝える。種類・勝敗・手番を自己申告しても採用しない。
2. サーバーは認証主体・参加権限を確認し、再送識別子と要求内容を照合する。
3. DBトランザクションで対局をロックする。ロック後にも再送状態を確認し、未処理の新規要求について最新state_version、PLAYING、手番、駒所有者、合法性を正本から検証する。
4. 作成時ruleset_versionに従い、移動・戦闘、盤面確定、敵HQ占領、双方の占領可能駒残存数、合法手有無、50手引き分け、未終局時の次手番の順に処理する。自動PASSが必要なら同じ処理内で解決する。
5. 盤面・結果・カウンター・手番・棋譜・PASS・再送記録を同一トランザクションで保存し、state_versionを更新してコミットする。失敗時は全体をロールバックする。
6. コミット済みの状態と認証主体に基づいて閲覧者別応答を生成する。終局前は敵秘密を除外し、終局後のみ参加者に全情報を返せる。

双方の占領可能駒が0なら引き分け、片側のみ0なら反対側勝利。双方に合法手がなければ引き分け、次手番側のみ合法手がなければ自動PASS。終局の優先順位・PASS発行時点の正本はGAME_RULES.mdの7節とする。

古いstate_versionを持つ新規要求は拒否する。ただし、すでに成功した同一client_move_id・同一内容の再送は再実行せず既存結果を確認できるようにする。同じIDで内容が異なれば拒否する。HTTPタイムアウトは未処理を意味しない。返す情報は再送時にも現在の認可条件で制限し、状態が進んでいれば最新取得へ誘導する。

補足：1回の状態変更トランザクションでstate_versionを1増加させる。着手に付随する自動PASSは同じコミットに含め、再送で重複イベントを作らない。配置変更・READY解除・開始も状態変更として版を更新する。PASSはプレイヤー着手ではなく、非戦闘カウンターを加算・リセットしない。状態と棋譜を別々のHTTP更新で確定する方式は禁止する。

### 非同期対局・再接続・終局後公開

正本はDBに置く。再ログイン時に参加対局一覧と最新の閲覧者別状態・state_version・棋譜を取得する。ネットワーク復帰時も再取得し、古い盤面から自動着手しない。手動更新と画面復帰時の取得を基本案とし、Realtimeは任意の補助とする。秘密テーブルの変更を直接配信しない。

終局前は完全棋譜・初期配置をサーバーの秘密領域に保持する。終局状態がコミットされた後、サーバーが認証済み参加者であることを確認した閲覧APIで、全駒種類、LOCK時初期配置、完全棋譜、各戦闘双方の種類を公開する。終局後も匿名・第三者への公開や秘密テーブルへの汎用アクセスは許可しない。リプレイ・エクスポートにも同じ認可を課す。

長期不在だけで対局を終了・削除しない。保存・バックアップ・復旧・スキーマ移行の運用を詳細設計する。既存ruleset_versionの判定・履歴解釈を保持し、新版へ暗黙移行しない。

### 招待URL・将来の手番通知

招待URLは十分な乱数を持つトークンを含む案とする。認証済み利用者だけを空き参加枠へ一度だけ原子的に参加させる。作成者=P1、招待参加者=P2。参加枠は2名。URLを知ることだけで盤面や秘密を読める設計にはしない。固定有効期限なし、参加後再利用不可、作成者による参加前の無効化可、再発行時の旧招待失効を正式方針とする。実際の招待は未実装。

メール・Pushによる手番通知は将来機能。通知なしで継続でき、送信失敗で着手を巻き戻さない。導入時はコミット後イベントの送信キューと重複抑止を設計する。通知には秘密を含めず、終局後の全情報閲覧も認証済みAPIで行う。方式・受信設定は未選定。

U1〜U5、R1、飛行機のHQ間直接移動の承認事項は反映済み。オンライン拡張に着手するときは物理スキーマ・API契約・RLS・実行権限を具体化する。今回、SQL・サービス設定は行わない。

## 第1〜第3段階の実装境界

`src/game/`は純粋なTypeScriptで、盤面・配置・合法手・戦闘・終局を計算する。React・ブラウザ・ネットワーク・DBには依存しない。新規ローカル対局の`rulesetVersion`はv0.2とし、未対応版を拒否する。既存v0.1ローカル保存は、全棋譜をv0.2で再検証できた場合だけ読み込み時にv0.2へ移行する。保存形式版は変更しない。将来のオンライン対人戦で作成時ルール版を固定し暗黙移行しない方針とは区別する。先手は呼び出し元から受け取り、乱数・認証・永続化は含めない。`src/cpu/`は閲覧情報への変換・CPU配置・思考・手番接続を分離する。サーバーAPIやDBの物理項目名をこのローカル型で確定しない。

Vitestでルール・CPU・保存形式・暗号化、React Testing Libraryで画面部品、Playwrightでブラウザ操作を検証する。`src/dev/`の架空配置・全駒表示は開発専用であり、オンライン対人戦の応答モデルではない。対CPU画面の配置下書き、準備中状態、確定済み対局は別のブラウザキーへ保存する。READYはオンライン対人戦用の状態であり、対CPU戦には導入しない。将来のオンライン対人戦ではサーバー配置自動保存と通信版管理・冪等化を別途実装する。

配置は「この配置で確定」、通常着手は駒→合法移動先→確認→確定の順とする。HQ間飛行機は中間駒に左右されず、目的HQが味方占有でなければC/D列を利用者が選択する。表示名は任意で未設定なら「あなた」「対戦相手」、メールを相手向け名称に使わない。
