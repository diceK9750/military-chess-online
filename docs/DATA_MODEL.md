# 保存データ設計

本書は実装前の論理データ設計であり、DB定義・SQL・サービス設定ではない。[GAME_RULES.md](GAME_RULES.md)をゲームルールの正本とし、[ARCHITECTURE.md](ARCHITECTURE.md)と[SECURITY.md](SECURITY.md)の必須条件を維持する。処理は[SERVER_LOGIC.md](SERVER_LOGIC.md)、画面の流れは[USER_FLOW.md](USER_FLOW.md)、選択事項の一覧は[IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md)を参照する。

以下の項目名・型・分割はゲームルールを変えない実装上の推奨。Supabase/PostgreSQLを第一候補とするが、物理テーブル名・通信形式は未確定。利用者体験のX番号はIMPLEMENTATION_PLANの承認状況に対応する。

## 1. 共通規約と関連

- 識別子は種類や配置順を符号化しない不透明なID（UUIDを推奨）。認証主体から利用者を特定し、要求中の利用者IDは信用しない。
- 日時はサーバーのUTC時刻で保存する。手番・READY・終局判定に経過時間を使用しない。
- 所有側はP1/P2で記録し、対局の参加者IDへ対応させる。表示回転で所有側や保存座標を変えない。
- 利用者1人は複数対局へ参加可能。1対局は異なる2利用者、各側23駒、開始時46駒。参加後の側・駒の所有者・本当の種類を変更しない。
- 利用者→参加対局→配置／現在駒／棋譜／招待／再送記録を参照で結ぶ。異なる対局の駒ID・イベントIDを混在させない。
- `state_version`は初期値0を推奨する非負整数。状態変更トランザクション1回につき1増加。再送・参照・拒否では増やさない。
- `ruleset_version`は作成時固定の不透明な版識別子。版と不変のルール定義・判定処理の対応を保管する。同じ識別子の内容を書き換えず、旧対局を新ルールへ暗黙移行しない。

## 2. 利用者

| 項目 | 型・必須性 | 制約・用途 |
| --- | --- | --- |
| user_id | ID、必須 | 内部利用者ID。削除・退会を対局の連鎖削除に直結させない |
| auth_subject | 認証主体ID、必須・一意 | 検証済みAuth利用者と1対1対応。同じログインで別端末から同じ対局を復元 |
| display_name | 文字列、未設定可 | X5承認済み。任意入力、未設定時は「あなた」「対戦相手」。メールアドレスを代用表示しない |
| created_at | 日時、必須 | 初回利用者レコード作成 |
| last_active_at | 日時、未利用時は空可 | 本人の利用・運用向け。相手へのオンライン監視情報としては返さない |

メール・認証トークン・Magic Linkの秘密値は対局レコードに複製しない。認証サービスで管理し、対局相手へ開示しない。メールMagic Linkを第一方式として承認済み（X1）、接続実装は今後行う。

## 4. 盤面と配置

正規座標はPlayer 1視点のA〜F・1〜8。P1の前方row+1、P2の前方row-1。C1/D1はHQ-P1、C8/D8はHQ-P2へ統合し、44通常地点+2HQ=46論理地点。仮想アンカーは地点として保存しない。各陣営は最後列5+他3行×6=23地点。突破口はB4↔B5、E4↔E5だけ。

初期配置と現在状態を分離し、初期配置を現在盤面の上書きで失わない。

| データ | 必須項目 | 制約 |
| --- | --- | --- |
| 配置ヘッダー（対局・所有側で一意） | game_id、owner_side、EDITING/READY/LOCKED、配置リビジョン、updated_at、ready_at、ready_revision、locked_at | READYがどの配置に対して成立したか記録。解除時は現行READY参照を外す。LOCK後は編集不可 |
| 配置中の駒（各側23件） | game_id、owner_side、piece_id、true_type、draft_position | 16種類23枚の構成はサーバーが生成。途中保存の未配置位置は空を許す案（X4）。非空位置は自陣内・重複なし |
| LOCK時初期配置（各側23件） | game_id、owner_side、piece_id、true_type、initial_position、locked_revision、locked_at、開始コミットのstate_version | 開始時に全地点を埋めたスナップショットを保存し、以降更新不可 |

全23枚・構成・禁止位置をREADY時とLOCK時に検証する。地雷と軍旗を自軍突破口入口へ置かず、軍旗を最後列（HQ含む）へ置かない。地雷のHQ配置は許可する。配置中の相手データは渡さず、READY等の進行情報だけを共有する。READY解除・編集はLOCK前に限る。

## 5. 現在の駒状態

| 項目 | 型・意味 | 制約 |
| --- | --- | --- |
| game_id / piece_id | 対局ID・不透明な駒ID | 組を一意にし、初期配置と対応させる |
| owner_side | P1/P2 | 利用者は対局の参加者から導出 |
| true_type | 16駒種のいずれか | サーバー正本。対局中は相手側ブラウザへ一切送信しない |
| position | 論理地点または空 | 生存駒だけ必須。対局内の生存駒は位置一意。HQ全体で最大1駒 |
| removed | 真偽値 | 除去後もレコードを保持。復活させない |
| removed_move_no | 手番号または空 | 除去時は必須。生存時は空。除去元の戦闘を追跡 |

removedが真ならpositionは空、偽なら除去手番号は空。除去前位置は棋譜に残す。軍旗の有効駒種は戦闘直前に計算し、駒の固定属性にしない。HQ進入ポートも現在状態に保存しない。必要な残存数はtrue_typeから算出し、性能を継承した軍旗を占領可能駒として数えない。

## 6. 着手・システムイベント・再送記録

正本の棋譜は追記式を推奨し、サーバー専用領域で保存する。完全棋譜と閲覧者別表示を同じものとして扱わない。

| 項目 | プレイヤー着手MOVE | システムイベントSTART / AUTO_PASS / END |
| --- | --- | --- |
| game_id / event_seq | 対局内で連続するイベント順 | 同じ系列で一意 |
| event_kind | MOVE | 種類を明記 |
| move_no | 受理順に1から増加 | 空。関連手番号を別項目で保持（開始時は空） |
| actor_side | 着手側 | AUTO_PASSは合法手がなく手番を飛ばされた側、START/ENDは必要に応じ空 |
| piece_id / from / to | 必須、論理地点 | 空 |
| 使用列 | HQ間の飛行機ならC/D必須、それ以外は該当なし | 該当なし |
| battle_occurred / outcome | 戦闘有無、攻撃側勝利／防御側勝利／相打ち。非戦闘は結果空 | 該当なし |
| 内部戦闘情報 | 防御駒ID、双方の実種類・有効駒種、軍旗継承情報、除去駒と結果位置 | ENDは結果・理由、AUTO_PASSは合法手なしの理由区分 |
| recorded_at | サーバー受理時刻 | サーバー記録時刻 |
| client_move_id | 必須 | 空。PASS用のプレイヤー要求を作らない |
| state_version_before / after | 同一コミットの前後版 | 付随イベントは同じ前後版を共有 |
| transaction_group | 同じ更新のイベントを束ねる識別 | 同じ更新なら共通 |

例：手番号10のMOVEにAUTO_PASSが続いても手数は10のまま、event_seqだけ2件分進む。両イベントの前後版は同じでstate_versionは1増加。開始時のPASSは手番号を消費しない。終局MOVEにはENDを続け、50手で終局した後にPASSを記録しない。

再送管理は対局・認証利用者・client_move_idの組を一意にする案とする。正規化した要求内容（駒ID、出発・到着、使用列、基準state_version）と成功結果のイベント参照・確定版を保存する。同じID・同じ内容は再実行せず、同じID・異なる内容は拒否する。内容比較でC/Dを除外しない。認証トークン等は比較対象に保存しない。生の秘密入りHTTP応答はキャッシュせず、再送時も現在の閲覧権限で表示を生成する。

対局中は成功済み再送記録を時限で消さない。長期再送と再開に備え、終局後も棋譜と対応を保持する案。失敗要求は着手棋譜を作らず、秘密を含まない運用記録と区別する。着手以外の作成等の重複防止IDは別用途として設計する（I3）。

## 7. 招待

| 項目 | 型・意味 |
| --- | --- |
| invitation_id / game_id / creator_id | 招待ID、対象対局、発行者 |
| token_hash | 十分な乱数トークンのハッシュ。生トークンはDB・ログへ保存しない |
| status | ACTIVE / USED / REVOKEDを推奨。使用済み真偽値はstatusから導出。固定有効期限は設けない |
| created_at / used_at / used_by | 発行日時、使用時だけ日時と参加者 |
| revoked_at | 失効時だけ日時を記録する案 |

有効性はACTIVE、未失効、参加枠に空きがあることをサーバーで判定する。X3の正式方針は固定期限なし、認証済み参加のみ、参加完了後再利用不可、作成者による参加前の無効化可、再発行時の旧招待失効。生トークンを復元する保存方式は採らない。失効済みリンクは参加済み対局の継続権限を取り消さない。参加後の対局にも現実時間の手番期限を付けない。物理スキーマは未確定。

## 8. 公開情報と秘密情報

「共有」は認証済みの当該2参加者への共有であり、インターネット公開ではない。

| 情報 | 終局前の共有 | 本人だけ | サーバー専用 | 終局後の両参加者 |
| --- | --- | --- | --- | --- |
| 状態、手番、版、許可された結果・盤面占有 | 可 | — | 正本管理 | 可 |
| 自軍種類・自軍除去駒 | 相手へ不可 | 可 | 正本管理 | 全駒公開 |
| 編集中配置 | 不可 | 可 | 正本管理 | 編集途中履歴は公開対象外 |
| LOCK時の初期配置 | 相手へ不可 | 自軍のみ可 | 両軍正本 | 両軍公開 |
| 内部戦闘情報、完全棋譜 | 不可 | 自軍と許可結果に絞る | 完全データ | 駒種類・戦闘内容を公開 |
| 使用列を含む合法的な着手経路・PASS | 可、敵種類は除去 | 同左 | 原本保存 | 可 |
| Auth秘密、招待ハッシュ、再送要求原本、内部ログ | 不可 | 限定APIの本人向け処理結果のみ | 可 | 公開しない |

DB秘密領域をブラウザ用ロールから直接読ませず、サーバーが許可リストで応答を生成する。RLSとAPI出力制限を併用し、終局後も秘密領域への汎用アクセスは許可しない。終局状態がコミットされ認証参加者と確認できた場合だけ、全駒・LOCK時配置・完全棋譜・各戦闘双方の種類を公開する。別対局IDや終了フラグ申告で解除しない。

## 9. 長期保存と拡張

数か月以上の再開を前提に、参加待ち・配置中・対局中を経過時間だけで削除しない。終局済みも初期案では保持する。状態、全棋譜、初期配置、再送記録、認証との対応、旧ruleset_versionの解釈を同時に復旧できるバックアップを設計する。復旧で盤面だけを戻さず、版・棋譜・再送記録を同じ時点にそろえる。

将来の保存管理はゲームstatusと別のライフサイクル情報で扱う案とする。放棄申請日時・削除予約日時・保持方針などの追加余地は確保するが、初版で放棄・削除を実行する機能や自動遷移は作らない。放棄を敗北・引き分けに読み替えない。退会・共有棋譜の削除・終局済み保存期間はX6で承認が必要。投了等を新設するなら別途ゲームルールの承認が必要だが、今回その追加は提案しない。

## 10. 設計の確認条件

16種類23枚、46論理地点、位置一意、除去状態の整合、LOCK後不変、手番号とPASS順序の分離、state_versionの単調増加、ruleset_version固定を自動検査できる構造にする。再送・並列更新・復旧を含む受入条件はSERVER_LOGIC.mdとIMPLEMENTATION_PLAN.mdで具体化する。本書にDB作成命令や実装コードは含めない。
